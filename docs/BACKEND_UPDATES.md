# Manual updates for the sealed grocery package

PR #2 supplies an offline-tested update mechanism for the existing VPS service.
The mechanism remains **unconfigured and inactive**. Push and PR events run synthetic checks;
they cannot deploy. The Mercado owner exclusively handles the separately approved
live grocery rollout. This automation task does not install a receiver, change
credentials/policies, dispatch a release workflow, restart the service or replay
a capture. Personal use requires no App Store publication or paid Apple membership.

## Current integration boundary

The accepted Mercado service now has six runtime files and an independent persistent USD2 guard. The reminder candidate has twelve files and a separate zero-default budget. This updater's four-file profile cannot adopt or update either: ordinary status/deploy/rollback admission rejects them before service calls or application/configuration mutation. Receiver bookkeeping may create private directories or a lock. Explicit recovery of a pre-existing legacy transaction has a separate fail-safe boundary and can stop the unit on code drift; it is not an adoption/update path for newer packages. Code integration preserves that rejection; it does not relax hashes, update the package profile, install a receiver, set deployment variables/secrets or enable a workflow. Future activation needs a separately reviewed compatible profile and preservation of both budget witnesses and unknown operations.

## Build and synthetic checks

The builder reads eight fixed, hash-pinned public Git blobs into a temporary
snapshot. It runs the pinned packager with a private-data-free environment, using
only read-only historical `git show` access. It never checks out or packages the
whole branch, imports application code, runs `--seal-manifest`, or reads local
credentials/ledgers. Output must contain exactly four ordinary Python files and
the byte-identical `manifest.json`. Both raw seal bytes and every artifact hash
are checked again before producing the schema-2 transport bundle.

```bash
python3 ops/deploy/build_bundle.py \
  --revision 1fe67948051f1d25140e13900d51275c498e0770 \
  --verify-tests --output /tmp/sealed-grocery-release.json
```

`--verify-tests` runs the package's 16 offline checks against the actual generated
historical runtime with synthetic helper/Notion fixtures. They cover partial batches,
lost acknowledgements, restart, raw-body identity and missing paired state. CI also
runs the combined backend, deployment, historical installer, six-file AI upgrade
and twelve-file reminder package regressions in separate Python processes. Production
credentials exist only in the final, separately gated SSH job, never in build/test
jobs. The code-only Actions artifact expires after three days and its digest is
checked before the transport key is exposed.

The legacy fixture pins an AST serialization produced by Python 3.9. CI uses an
explicit Python 3.9 executable for the backend and package checks; Python 3.12 adds AST fields
and cannot reproduce that fixture digest. The fixture and seal are unchanged.
Deployment receiver regressions still run on the runner's default interpreter.
This selects a CI toolchain only and does not change the VPS interpreter or settings.

## Atomic activation and compatible recovery

The receiver stages all four files plus their manifest in a new immutable directory
under an audited readable code root, such as `/opt/personal-watch-releases/<bundle-id>`.
Directories/files are root-owned `0755`/`0644`; code is separate from private receiver
state (`0700`) and both application databases. An existing stage must match the
complete seal; it is never patched in place. Only strictly recognized ordinary
Python cache files for those modules may accompany it. They are generated runtime
output, excluded from the seal/bundle and purged while stopped before receiver-led
starts. Unknown files or cache symlinks fail closed and remain untouched.

After persisting a code snapshot and transaction journal and stopping the service,
the receiver atomically points the existing BFF entry at a guaranteed nonexistent
receiver-owned inhibitor path and fsyncs the entry directory. It then persists the
compatibility floor before atomically selecting the complete package's
`mobile_capture_staging_server.py`. A reboot between those steps fails to open the
inhibited entry instead of starting an old incompatible writer. CPython resolves the script's link
target for sibling imports; the exact sealed artifact was tested with trap sibling
modules beside the original entry. Keep the application's current interpreter
invocation; **do not add Python `-I` to the application**. The separate receiver
itself uses `python3 -I`. Preserve the explicit existing `--ledger` argument,
because application defaults follow the resolved code directory.

Only that entry link changes. Original sibling files and operator backups remain
untouched. At every durable pointer state the entry denotes the complete old
runtime before activation, the inhibited entry, or the complete staged package;
no process can load a halfway-copied set after a crash/reboot. Host `flock` serializes all receiver operations and a
fresh installed-code fingerprint prevents stale updates. GitHub additionally
queues release runs with `cancel-in-progress: false`; older pending runs may be
replaced by GitHub, but an active release is not cancelled by a newer one.

Before switching to any batch-capable package, the receiver persists a monotonic
`grocery-batch-v1` compatibility floor. It does not inspect private rows to guess
whether a batch has already started. A request can arrive while health is still
being verified, so **failed health is not permission to return to a single-item
writer**. The floor cannot be cleared over the release transport.

An existing regular four-file deployment is a compatible adoption baseline only
when all four bytes/hashes match the trusted seal. A known legacy one-file baseline
is preserved as code evidence, but once the floor exists, deploy/rollback/recover
must not start it. Automatic recovery restores and verifies a compatible predecessor;
if none exists, the service stays stopped, the journal/snapshots remain, and the
receiver reports the incompatible recovery boundary. The normal activation handoff
therefore follows the Mercado owner's successful four-file rollout, providing a
compatible baseline before enabling routine automation.

If the service manager fails to stop the process, the receiver attempts to inhibit
the entry and preserve the floor/journal, returning `stop_failed_recovery_required`.
The existing process may remain active; that result does **not** claim a successful
stop or recovery. Confirm the actual `inhibited` status; filesystem failures may
also prevent that protective write. The live owner must resolve the condition
before further release operations.

Success requires the exact process arguments, a changed process identity, complete
code/seal identity, unchanged helper hash and exact loopback/HTTPS health. Network
checks run in transient isolated subprocesses with wall-clock deadlines, lifetime
limits and cleanup. They are not daemons. Health proves reachability and the current
gate profile; it does not prove grocery writes or physical-device acceptance.

## Paired state and retention

The existing mobile ledger keeps its exact absolute path. The paired grocery journal
is `str(ledger_path) + '.grocery.sqlite3'`; both remain outside immutable code.
Parent `processing`/`grocery_pending` identity and child prepared/uncertain/committed
claims must survive code updates, failures, retries and rollback. Neither database,
their WAL/SHM files, helper state nor credentials enter bundles, snapshots, logs or
CI artifacts. The receiver never opens, migrates, deletes, initializes or restores
these databases.

The live rollout owner must retain a consistent private backup of **both** databases
with writers quiesced, following the package's existing activation instructions.
An individual database copy without its journal/WAL consistency is not a valid
recovery plan. Never restore only one database, discard pending claims, re-dictate
a batch, clone request IDs or replay through the old helper. Code rollback does
not undo an external grocery mutation.

Code retention keeps the configured recent snapshots plus active, previous,
adoption baseline and any pending transaction references, in both the private
snapshot store and immutable code root. Verified failure recovery can prune old
failed candidates. Pending/failed recovery retains its evidence. Only validated
receiver-owned names and seal-verified directories may be pruned; unknown files,
original sibling modules, operator backups and all application data are untouched.
Cleanup failure must be reported truthfully rather than invalidating verified
recovery or pretending storage was reclaimed.

## Operation after activation

Actions → **Manual backend update** → **Run workflow**, select **main** for the
reviewed automation implementation. The package revision is already fixed by its
trusted profile; selecting the stacked feature branch as workflow source is rejected.

| Operation | Inputs | Exact confirmation |
| --- | --- | --- |
| Inspect | `action=status` | `status` |
| Deploy the sealed package | `action=deploy`, pinned `revision`, fresh `expected_current` | `deploy <revision>` |
| Restore compatible predecessor | `action=rollback`, retained `release_id`, fresh `expected_current` | `rollback <release_id>` |
| Recover interrupted operation | `action=recover`, after inspecting status | `recover` |

`current` is SHA256 of the canonical sorted map of actual runtime filenames/hashes.
`release_id` identifies an immutable code snapshot/bundle; keep successful receipts
with the reviewed source/manifest pins. If SSH disconnects or a job times out, the
outcome is unknown: inspect status before any new mutation. The sender never retries
an uncertain deployment. Status/results expose only fixed codes, hashes and flags.

If recovery reports an incompatible predecessor, keep the service stopped and
leave both databases, floor and journal intact. The Mercado owner must review a
compatible sealed rescue through the existing console, fix the concrete startup/
access problem and verify the same batch-capable runtime before resuming traffic.
Do not clear state or use the old one-file backup as a shortcut. No automatic
recovery step may turn this condition into permission to replay uncertain work.

From an already trusted machine with separately approved private `WATCH_SSH_*`
environment values, the same sender supports `--action status` and deliberate
`--action deploy --bundle /tmp/sealed-grocery-release.json --expected-current <HASH>`.
Do not include credential values in commands, enable shell tracing or verbose SSH.
